# 财报分析真实功能开发计划：一个人 + AI 编程助手

更新日期：2026-09-23。依据：当前仓库的财报分析 mock、financial-report-analyzer 脚本及现有文件、Agent 服务。本文替代之前的多人团队计划，只规划工作，不表示功能已经实现。

## 1. 交付目标和时间估算

开发方式：你决定范围、提供样本、运行应用、核对结果；AI 阅读代码、实现小任务、补必要测试、定位错误。每轮拿到一个可运行结果，通过后再进入下一轮。

先完成一条用户路径：**上传一份真实财报 → 看到真实指标和分析 → 点击数字查看原文 → 继续追问。**

首版沿用现有 mock 的布局和交互。优先做中文、人民币、非金融企业的文本型年度报告 PDF，使用真实披露的比较期；资料不够时展示缺项。先用 1 份财报跑通，再用另外 2 份不同公司的财报验证泛化。

按每天能投入约 3–4 小时、现有前后端和模型可用估算，安排 **10–15 个开发日**，约 2–3 周。这里包含你运行、检查、反馈和修复的时间，不是 AI 生成代码的时间。若环境尚未跑通、样本主要是扫描件或表格解析效果差，应单独增加时间，并在第 3 轮后重新估算。

分两次交付：

- 第一次：预计累计 5–7 天，上传后能看到真实指标、确定性计算和原 PDF 来源，作为可用内测版。
- 第二次：预计累计 10–15 天，接上完整章节、模型分析、追问、实际执行状态、保存与下载，形成个人可维护的 v1。

OCR、行业对标、联网抓取、多公司对比、跨文件多年合并、精确表格框选、复杂断点续跑放到 v1 之后。

## 2. 当前代码怎样接着用

| 会话文件服务、附件适配器、Agent 工具链 | 复用上传、文件读取、模型接入和运行展示，先确认实际运行路径 |

最小实现建议：一个财报分析服务、一份版本化报告 JSON、现有文件存储、当前 React 页面。先用现有数据库保存 run 状态和报告快照，避免第一轮就拆出大量实体表和通用工作流平台。

## 3. 按顺序执行的 8 轮开发

### 第 1 轮：固定运行入口和样本（0.5 天）

给 AI 的任务：

> 检查本仓库财报分析页面、文件上传、模型和 Skill 的实际启动入口，整理最短本地运行步骤。使用一份可获得的真实年度报告作为首个样本，明确它如何进入现有上传链路。只修复阻塞这条路径的问题，记录运行命令和缺失配置。

你需要做：启动应用，准备原 PDF，人工抄下 5–8 个关键数字及所在物理页码。优先使用 mock 对应报告；无法取得时用另一份真实报告，不拿 mock 数字当标准答案。

完成标准：页面能打开，现有模型能响应，样本能通过上传入口读取；有一张简单的“指标、期间、单位、口径、值、页码”核对表。

### 第 2 轮：让页面能接收另一份数据（1 天）

给 AI 的任务：

> 基于现有 types.ts 定义最小 ReportData，包含 report、documents、facts、calculations、findings、metrics、trends、steps。抽离组件对 mock-data.ts 的直接依赖，通过 props/context 或项目已有数据层提供数据。先让原 mock 经过新数据入口渲染，再使用改过公司名、年份、期数和缺失字段的 fixture 验证页面没有残留写死内容。不要调整视觉设计。

改动重点：`FinancialAnalysisPage`、`ReportSections`、`EvidencePanel`、`AgentRunPanel`、`ExecutionProcessPanel`。给来源和指标提供独立跳转能力，不强迫所有指标先属于某条研究发现。

完成标准：换一份报告数据，公司、年份、指标、图表和表格都同步改变；缺失指标不崩溃、不回退到示例值。离线 demo 仍使用 mock 数据源。

### 第 3 轮：从真实 PDF 提取带来源的事实（2–3 天）

给 AI 的任务：

> 改造财报提取链路，先支持营收、归母净利润、扣非归母净利润、经营现金流、总资产、总负债及报告中可用的比较期。逐页保留文本和表格，输出原文值、标准化值、单位、期间、口径、物理页码和摘录。数值缺失返回 null 和原因。用首个真实样本验证，不为该公司硬编码页码或数字。

实现顺序：先定位关键财务数据表和合并报表，再按表头识别期间与单位，最后提取目标行。可让现有模型在候选表格中辅助识别语义，但每个输出都要绑定可核对的原文，不让模型自行填空。

最小事实字段：`id / metricCode / rawValue / normalizedValue / currency / unit / fiscalPeriod / statementScope / evidenceExcerptIds / qualityStatus`。涉及归母与合并总额时增加明确的归属口径。证据保存文件 ID、物理页码、原文片段；暂时不要求 bbox。

你需要做：逐项与 PDF 核对，重点检查负数、万元/元、当期/上期、归母/合并总额。把每个错误连同对应表格片段交给 AI 修复。

完成标准：第一份报告的目标核心值与人工核对表一致；额外两份报告能提取或明确报告缺失/不支持，不能把失败值伪装成可信数据。

这轮是主要不确定项：若提取持续不稳定，先收窄支持版式或明确待核对字段，再继续后续功能。不要用增加分析文字掩盖事实错误。

### 第 4 轮：计算 + API + 页面连通（1.5–2 天）

给 AI 的任务：

> 基于已提取事实实现同比、非经常性净影响及占比、现金利润比、资产负债率，输出 formula、inputFactIds、steps、result 和 displayResult。金额和比率使用精确计算，API 用十进制字符串传输。接入现有文件上传，创建分析任务，保存状态和报告 JSON，让页面根据 run ID 查询真实结果。先用轮询展示处理阶段，沿用项目现有数据访问方式。

最小新增接口草案：

- `POST /financial-analysis/runs`：提交 session ID、file IDs，返回 run ID。
- `GET /financial-analysis/runs/{id}`：查询任务状态、实际阶段与错误。
- `GET /financial-analysis/runs/{id}/report`：读取已保存的报告 JSON。

实际路由前缀按仓库惯例；输入文件上传和下载继续使用现有服务。后端创建 run 时验证文件归属，后台处理期间保持合法文件访问生命周期，不复用已经被聊天回合清理的临时路径。

数值规则：缺失输入和零分母显示不可计算；不同币种、期间和口径不能直接混算；同比为百分比、费用率差为百分点。ROE 优先使用可追溯披露值，不能把净利润/期末权益冒充披露的加权平均 ROE。

完成标准：上传 PDF 后，Overview 与关键报表显示真实数字；点击指标能看到公式、输入值和来源。页面刷新能重新读取已完成结果。首批公式覆盖正常、负值、缺项、零分母和单位换算用例。

### 第 5 轮：接通真实 PDF 来源预览（0.5–1 天）

给 AI 的任务：

> 把 SourcePreviewPanel 接到实际上传的 PDF，复用现有预览能力或采用最小可用的页级展示。点击证据时打开对应物理页，同时保留摘录。暂不实现精确区域框选；无法跳页时保留下载和明确页码，不把重排摘录展示成原 PDF。

你需要做：从 3 个不同指标点进来源，确认文件、页码和摘录一致；区分 PDF 物理页与报告印刷页码。

完成标准：能从页面中的数字回到真实原文件核对。至此交付第一版可用闭环。

### 第 6 轮：补全五个章节和真实分析（1.5–2 天）

给 AI 的任务：

> 扩展费用、流动资产/负债、存货等可用事实和计算，驱动现有五个报告章节。使用项目已有模型服务，基于 facts、calculations 和相关附注生成结构化 findings，包含 summary、factIds、calculationIds、evidenceExcerptIds、supportStatus、counterEvidence 和 unresolvedQuestions。验证引用存在和数字一致；证据不足就减少结论或标记待核查。保留旧 Skill HTML 输出兼容。

实现要点：先生成结构化分析，再由固定 React 组件渲染。年度趋势按真实期数显示。失败的分析阶段允许保留已经提取的事实和计算结果。

你需要做：核对最重要的 3 条结论，每条都点开依据；换第二家公司，确认结论会随数据变化，不再重复 mock 的“利润下降”等固定判断。

完成标准：Overview、盈利质量、现金流、资产负债、关键报表均来自实际报告。流动/速动比率等缺少输入时显示缺项，不沿用示例常量。

### 第 7 轮：把固定问答换成真实追问（1–1.5 天）

给 AI 的任务：

> 改造 AskDbGPTDock，新增与 run ID、报告 revision 绑定的提问入口，复用现有模型调用。先给模型当前问题相关的事实、计算、研究发现和原文摘录，不把整份 PDF 无限制塞入提示词。回答返回文本与有效引用，并接到证据/来源面板。第一版只读当前报告上下文，资料不足时明确说明。

提问入口建议：`POST /financial-analysis/runs/{id}/questions`。有现成流式能力则复用；流式适配有阻塞时先完成普通响应与明确的等待状态。计算问题调用受控公式函数，不由模型心算后直接输出。

你需要试的 5 类问题：利润变化、现金转化、费用压力、某数字来源、报告未披露的信息。报告不能回答的内容应承认缺少依据。

完成标准：固定关键词答案被替换；数字与报告一致；引用可跳转；切换 run 不会使用上一份报告的信息。

### 第 8 轮：补齐每天使用需要的能力（1–2 天）

给 AI 的任务：

> 用现有执行记录驱动 Agent 面板和执行过程，展示真实阶段、耗时和错误。完善已完成报告保存/重新打开、失败后显式重试、真实文件列表以及 JSON/HTML 下载。检查刷新、解析失败、模型超时、缺数据、重复点击和服务重启后的状态。为当前链路添加最小有意义的集成回归，交付本地运行说明。

首版实现边界：

- 已完成结果必须持久化；浏览器断开不等于业务已完成或失败。
- 后台任务沿用已有机制；若进程重启后无法续跑，将中断任务明确标为失败并可重新运行，不能永久显示 running。
- 重试首版可以重跑整份报告，保存新的 attempt；阶段级断点续跑后补。
- 文件列表只展示真实存在的文件。JSON/HTML 来自同一报告快照；PNG 在实际生成并登记后展示。
- 日志保留阶段、工具、耗时和错误摘要，避免展示内部推理或未经处理的敏感路径。
- API、文件和报告访问沿用相同的 owner/session 校验，不因为个人开发而省掉现有权限边界。

完成标准：连续分析 3 份真实报告，走完上传、查看、核对、追问、下载、重新打开；模型失败时能解释失败并保留已有数据。

## 4. 每次怎样让 AI 做，才能方便你接着改

每次只提交一个可验收任务，通常控制在 1–3 小时能运行检查的范围。第 3 轮这样的较大任务要继续拆成“页级解析、表格识别、事实标准化、跨样本修复”四次。

通用任务模板：

> 当前目标：[本轮一个具体结果]。
> 相关代码：[已知文件/模块]，先检查调用链再改。
> 约束：复用已有组件和服务；保留离线 mock 演示；真实模式缺数据不得回退到 mock；不要顺手重构无关模块。
> 验收：[输入、操作、期望输出，以及一个失败场景]。
> 完成后：执行与改动相关的检查，给出改动文件、运行命令、验证结果和剩余问题。缺少凭证或样本时明确指出，不宣称真实链路已验证。

你的固定节奏：让 AI 实现 → 自己在页面走一遍 → 对照 PDF 核对 → 把具体错误交回 AI → 通过后做一个本地提交，再进入下一项。每轮结束记录“已完成、当前故障、下一任务、验证命令”，便于新会话继续。

## 5. 保留的质量底线与后续任务

v1 必须做到：真实模式没有示例数字兜底；每个已展示核心值可回看来源；计算可复算；缺失值和口径冲突明确呈现；结论不能把猜测写成报告事实；任务失败可见；已完成结果可保存。

首版用 3 份实际报告做逐项检查，结论只覆盖这组样本的验证范围，不能据此宣称普遍准确率。保留负数、单位、期间、零分母和引用错误的回归样例。

后续按真实使用中最影响体验的问题排序：

| 使用中遇到的问题 | 再建设的能力 |
| --- | --- |
| 经常上传扫描件 | OCR 与图像表格识别 |
| 指标提取后经常需要纠正 | 人工复核界面、修订历史与自动重算 |
| 经常查不到解释业绩的附注 | 文档级检索与更完整的附注索引 |
| 经常需要多年比较 | 多文件期间对齐、重述处理和版本合并 |
| 处理时间较长、失败重跑成本高 | 阶段缓存、可恢复任务和事件断线补发 |
| 经常花时间在 PDF 找行 | bbox 提取与原文区域高亮 |
| 开始多人部署使用 | 扩大评测集、并发与成本测试、运营监控及部署加固 |
